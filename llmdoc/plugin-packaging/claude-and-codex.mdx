# Claude 与 Codex 表面

## Claude 是当前手工维护源

仓库根已经按 Claude 插件形态组织：

- `.claude-plugin/*.json` 提供插件元数据与 marketplace 入口
- `skills/llmdoc/SKILL.md` 是手工维护的 operating skill 与 Retrieval Gate 源
- `skills/init|update|prune|upgrade/SKILL.md` 是四个显式工作流的薄壳 SOP
- `agents/investigator.md` 与 `agents/recorder.md` 是角色契约
- 根 `hooks/hooks.json` 只负责把生命周期事件转给 `npx -y @tokenroll/llmdoc hook ...`

这些文件描述“何时、为什么、授权到哪里”，而不是重写 CLI 的算法。

`.claude-plugin/marketplace.json` 也是跨宿主 marketplace 身份的 canonical authoring surface。公共 marketplace 名是 `llmdoc-plugin`，其中的插件名是 `llmdoc`，所以 Claude 安装坐标为 `llmdoc@llmdoc-plugin`；文案应保持跨宿主定位。

## CLI 是共同 runtime

不管宿主是 Claude 还是 Codex，机械能力都收敛到 `@tokenroll/llmdoc`：

- 检索与路由
- state/delta/fingerprint
- hook 信号
- 轻量结构改写

因此包装层变更时，先检查命令文档是否只保留判断性内容；不要把 diff、schema 校验或 git 逻辑重新写进 prompt。

Retrieval Gate 是需要跨宿主保持语义一致的判断性契约：第一次发现式检索与进入新子系统时按意图选择 CLI 入口，圈定工作集后允许原生工具核对实时精确事实，并且不把检索命令跑成固定序列。这个契约现在同时覆盖 skill 与角色两条线：Claude canonical skill 与生成的 `.agents/skills/llmdoc/SKILL.md`、两个 Claude 角色契约（`agents/investigator.md`、`agents/recorder.md`）与生成的 `.codex/agents/*.toml`、以及面向无插件平台的中英文 README 配方，都应保持这些边界及外部 `npx -y @tokenroll/llmdoc` 调用语义一致；不得为了满足 gate 而改写业务项目依赖。宿主 front matter 和具体措辞可以不同。

## Codex 兼容面的实际要求

README 与示例文件都已经把方向收敛到“Claude canonical，Codex 兼容/转换表面”。当前实现里，ACPlugin 生成的是：

- `.agents/plugins/marketplace.json` catalog；其 marketplace 名必须与 Claude canonical marketplace 一致为 `llmdoc-plugin`，插件名保持 `llmdoc`
- `.codex-plugin/plugin.json` manifest
- `.agents/skills/` 下的五个 skills（operating + 四个工作流，与 Claude 侧同名一比一转换，无 `cmd-*` 前缀；`upgrade` 的 `disable-model-invocation` 同时映射为 frontmatter 与 `agents/openai.yaml` 的 `allow_implicit_invocation: false`）
- `.codex/agents/` 下的 project-scoped `investigator` / `recorder` TOML

Codex 插件原生支持 hooks：默认从插件根 `hooks/hooks.json` 读取（Claude 兼容 schema，SessionStart/Stop/PreCompact 与 `additionalContextLimit` 均支持），manifest 无需 `hooks` 字段——本仓库根既是 Claude 又是 Codex 插件根，同一份 hooks.json 一份两用。插件 hooks 是非托管的，用户安装后须经 `/hooks` 审查信任才会运行。

acplugin 转换注意（重生成后需人工核对）：`model: inherit` 硬编码与 hooks 降级已在 acplugin PR #9 修复（合并前旧版仍有此问题）；manifest version 读取 `.claude-plugin/marketplace.json`，bump 版本时不要漏掉它。转换必须在临时副本运行后替换式同步，acplugin 不清理上次的陈旧输出。

当前 Codex 表面的同步状态：`.agents/skills/` 与 `.codex/agents/` 是随 canonical 变更手工替换式同步的（正文与 Claude 侧逐字节一致、TOML 可解析），尚未用修复版 acplugin（≥1.6.1）重生成确认——npx 当前只解析到旧版本，旧版会重新引入 `model: inherit` 与 hooks 降级回归，因此在拿到修复版之前不要盲跑重生成。生成表面里旧有的 `npx --no-install` 调用已全部清除，与 canonical 统一为 `npx -y`。

`scripts/check-codex-surface.mjs` 会自动拒绝任一 marketplace 名不是 `llmdoc-plugin` 或两侧名称不一致；`tests/parity-checklist.md` 则要求发布前人工确认两侧 marketplace 名与插件名分别为 `llmdoc-plugin` 和 `llmdoc`。

根 `hooks/hooks.json` 不靠 ACPlugin 复制；Claude 与 Codex 都直接共用这份根 hook 壳，并统一通过 `npx -y @tokenroll/llmdoc` 调用 CLI hook 子命令。`-y` 允许缺包时非交互获取正确的 scoped 包到 npm 缓存，且不触碰业务项目的依赖清单；需要确定版本时应在 npx 包名中 pin，而不是执行会改写项目 `package.json` 或 lockfile 的安装命令。

维护时要遵守两点：

- `.agents/plugins/marketplace.json`、`.codex-plugin/plugin.json`、`.agents/skills/`、`.codex/agents/*.toml` 必须继续反映与 Claude 相同的公开契约，至少在 marketplace 身份、命令集、Retrieval Gate、授权语义和 hook 行为上保持一致。
- 不手工维护第二份 Codex 角色文本；Codex 角色文件是从两个 Claude 角色契约再生成的兼容表面，而不是独立真相源。
