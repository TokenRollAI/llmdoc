# llmdoc 仓库整体架构

这个仓库把 `llmdoc` 拆成四层相互配合的能力：

- `cli/` 是运行时实体，负责扫描 `llmdoc/`、校验 front matter 与 `meta.json`、做检索与影响面分析，并暴露 hook 与维护命令。
- 仓库根的 Claude 表面负责判断性 SOP：`skills/` 下五个 SKILL.md（`llmdoc` operating skill 加 `init/update/prune/upgrade` 四个显式工作流）描述工作流，`agents/investigator.md` 与 `agents/recorder.md` 描述两个角色，`hooks/hooks.json` 只负责用 `npx -y @tokenroll/llmdoc hook ...` 把生命周期事件转发到 CLI。
- ACPlugin 生成的 Codex 兼容表面位于 `.agents/plugins/marketplace.json`、`.agents/skills/`、`.codex/agents/` 与 `.codex-plugin/plugin.json`，它们承接 Claude 根表面的 marketplace、命令、operating skill、角色契约与 manifest。
- `llmdoc/` 是仓库自身的 dogfood 知识面，用 V3 两层目录反过来解释这套实现本身。

跨宿主包装共用一个公开身份：Claude canonical marketplace 与 Codex catalog 都使用 `llmdoc-plugin`，其中的可安装插件名是 `llmdoc`；Claude 的完整安装坐标因此是 `llmdoc@llmdoc-plugin`。

V3 的重要分工是“提示词只做判断，CLI 负责机械”。命令文档会决定何时走 `init`、`update`、`prune`、`upgrade`，真正的目录扫描、JSON schema 校验、git revision 检查、delta 计算和 hook 输出都落在 `cli/src/`。

operating skill 与 README 内嵌配方用 Retrieval Gate 落实这个分工：第一次发现式检索及调查进入新子系统时，按意图从 `search`（概念或契约）、`context --files`（具体源码文件）、`tree`（范围不明）、`index`（已知 topic/kind）或 `show`（已定位文档正文）中选择入口，而不是把命令跑成固定序列。CLI 圈定工作集后，原生工具负责源码、行号、测试、计数和 git 状态等实时精确事实。

当前仓库已经按 V3 的公开接口改写：README（含给无插件平台的内嵌 AGENTS.md 配方）、命令面、hook 面与 CI/release 都以 `@tokenroll/llmdoc` CLI 为共同 runtime。operating skill 与 README 检索配方通过 `npx -y @tokenroll/llmdoc` 按需调用这个项目外部工具；缺包时只写入 npm 缓存，不得改写被服务项目的 `package.json` 或 lockfile，需要固定版本时在 npx 包名中 pin 即可。V2 的根 `index.md`、`startup.md`、`sync.md`、`worker`、`reflector` 不再是有效契约。

按主题继续阅读（topic 无入口节点，用 `llmdoc index --topic <t>` 看各文档描述）：

- `cli-runtime/`：文档树扫描、状态与校验读 `state-and-validation.mdx`；命令面读 `retrieval-and-mutation.mdx`。
- `workflows/`：init/update 契约读 `init-and-update.mdx`；prune/upgrade 读 `prune-and-upgrade.mdx`。
- `plugin-packaging/`：提示词与双平台表面读 `claude-and-codex.mdx`；开发发布读 `development-and-release.mdx`。
